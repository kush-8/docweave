# Deletion and retention

Explicit chat deletion first enforces current ownership, fences jobs and tombstones access. Migration `0041_chat_cleanup` also erases messages, answers, citation payloads, dependency references, progress and summaries without deleting conversation/turn/job IDs, reservation rows or replay hashes. Existing response-checkpoint deletion and late-write fences remain. Erasure is irreversible; downgrading the schema does not restore deleted text.

The personal worker's existing startup/ten-second maintenance drains up to 100 old chat tombstones and 100 expired rows from each login-flow, session and rate-limit table per transaction. It works without a fresh owner login. The same worker now runs artifact reconciliation, so a deployment does not need the ingestion worker solely for orphan cleanup. Both cleaners preserve referenced snapshots and a five-minute write grace period, and tolerate another cleaner removing the same file. Other file errors still surface for recovery.

Run the appropriate workers while services are operating; an offline machine cannot perform cleanup. The 24-running-hour requirement still needs acceptance under the actual deployed topology/backlog, not only a small fixture. Do not erase financial, operator, preservation or unknown-completion identity to clean content or retry work.

The [schema audit](../reports/2026-11-03-retained-schema-audit.md) identifies currently referenced structures and legacy retirement candidates. Development inspection found no invitation/manual-documentation rows, but legacy SQL/grants and historical restoration dependencies still exist. No retained table was dropped. Removing a whole obsolete SQL/model/table group requires its own reference-complete migration and preservation decision, not an ORM-only deletion.

Seven-day backup expiry and replay of later deletions into restored backups remain **unimplemented/unverified**. Existing private accounting archives are explicitly retained for unresolved obligations; do not automatically delete them or infer settlement because their age exceeds ordinary backup retention. No blanket backup-directory purge is authorized by this runbook. Before resuming a restored service, reconcile deletions since that backup, reapply the corresponding chat/document tombstones and artifact/index cleanup in the isolated copy, verify current authority/consent/guardrail fences and compare financial/replay identity. An old backup must not silently revive deleted content. A complete automatic backup/deletion policy remains a release gate.

Current development `0041` rollout passed an actual backup, isolated restore, row/artifact comparison, function/grant/sequence comparison and three restricted-login checks. Evidence is private under `backups/release-cleanup-20261102T200853Z/`. A bounded maintenance acceptance pass removed an expired login flow and preserved all five conservative probe claims and disabled consent. This does not establish the missing backup-expiry or post-restore deletion policy.
