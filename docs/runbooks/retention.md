# Deletion and retention

Explicit chat deletion first enforces current ownership, fences jobs and tombstones access. Migration `0041_chat_cleanup` also erases messages, answers, citation payloads, dependency references, progress and summaries without deleting conversation/turn/job IDs, reservation rows or replay hashes. Existing response-checkpoint deletion and late-write fences remain. Erasure is irreversible; downgrading the schema does not restore deleted text.

The personal worker's startup/ten-second maintenance processes at most 100 old chat/document tombstones and 100 expired rows from each login-flow, session and rate-limit table per transaction, repeating until overdue cleanup is drained. It works without a fresh owner login. The same worker runs artifact reconciliation, so a deployment does not need the ingestion worker solely for orphan cleanup. Both cleaners preserve referenced snapshots and a five-minute grace period for unknown recent writes. Recorded deleted artifacts bypass that grace, including freshly restored files. Concurrent removal is tolerated; other file errors close maintenance health and stop the worker.

Run the appropriate workers while services are operating; an offline machine cannot perform cleanup. Startup waits for a strictly later successful worker maintenance pass. Protected HTTP requests, hosted authorization and all four queue task bodies reject overdue cleanup or failed/missing/stale maintenance health. The local monotonic health record assumes one host; distributed workers require database-backed health.

Ordinary recovery backups now have explicit seven-day expiry through `python -m docweave.storage.backups`. The personal worker checks the repository's `backups/` directory at startup and during maintenance. It never classifies directories by age/name or enrolls them automatically. After actual restore/preservation verification, seal an ordinary backup with `--enroll BACKUP_DIRECTORY_NAME --created-at ISO_TIMESTAMP_WITH_OFFSET`; use its actual creation time, not enrollment time. Enrollment verifies the acceptance evidence and dump hash, then fingerprints every file. Do not enroll an unresolved accounting archive. Keep sealed backups immutable, with no concurrent writers; save later evidence outside the sealed directory. Unknown directories and standalone reports are preserved.

Before expiry starts, altered/added/missing files, links/junctions and invalid receipts block deletion. Once the seven-day boundary is reached and the seal matches, a durable deletion marker is fsynced before unlinking only verified files. Locks and I/O failures report `retry_pending`; the next pass resumes from remaining original bytes. Added/modified evidence still blocks that retry. The command exits nonzero for blocked/pending results; worker logs record those statuses without file contents. Investigate these logs rather than treating a blocked backup as expired. A crash while writing the intent may require operator receipt repair before any deletion; a crash after removing the last receipt can leave an empty directory. Expiry does not create or verify fresh backups.

Migration `0042_deletion_receipts` adds content-free erasure receipts. All three HTTP deletion paths (chat, uploaded document, imported source) write immutable project/object/artifact UUID intents to the external `DELETION_JOURNAL_ROOT` before the deletion transaction commits. Artifact IDs are recorded in bounded batches, so a long replacement history does not prevent deletion. The matching hashes commit with the existing SQL payload-erasure/job-fencing functions. Failure after journal write leaves a valid pending intent; it does not silently discard the authorized deletion. Replay reconstructs any interrupted artifact batches from the restored target before fencing it and removing files. Accounting, IDs and replay hashes remain.

On a brand-new installation, after migrations and before services start, provision the dedicated journal once using `python -m docweave.deletions --initialize` in the backend source environment. Default location is repository `deletions/`, outside ordinary backups and ignored by Git. Preserve this latest journal independently of database backups and retain its intents while any older backup/archive can be restored. Never restore an older journal over the latest one, initialize an empty replacement, edit receipts to bypass a mismatch, or enroll the live journal for ordinary backup expiry. Only trusted operators/services may write it.

For restoration:

1. Stop the API and **both** worker types. Keep them stopped throughout replay; a count of currently running jobs is not a barrier against a connected idle worker claiming another job.
2. Restore the database and artifacts in isolation, retaining the latest external journal. Apply current migrations, keep provider profiles disabled and perform the preservation/authority/consent/guardrail checks. Missing preserved ownership requires deliberate reconciliation through the existing preservation tools.
3. Run `python -m docweave.deletions --replay --database-url-env RESTORED_MIGRATION_DATABASE_URL --journal C:\secure\current-deletions --artifacts C:\restore\artifacts`. The named environment variable must identify the isolated restored database under the migration role. The artifact directory must already exist without links.
4. Verify successful reconciliation and expected erasure against the backup baseline, including unchanged financial/replay identity, before starting services. Retry the same command after an artifact I/O failure; do not drop uncertain charges or repeat hosted calls.

API startup, protected authenticated requests, both worker startup/maintenance paths and every existing hosted-call authorization boundary fail closed on missing/corrupt/unmatched journal data or remaining recorded artifacts. Sign-in identity inspection/logout remain available during a request-level block. Hosted bytes already admitted or in flight cannot be recalled by a later deletion. Journal availability and preservation are operational requirements; ordinary backup expiry cannot replace them.
