# Manual backend projects

These four operations implement manual context. Start the API using the [README](../../README.md#run-the-api-skeleton), sign in using the [auth runbook](auth.md), then create a [workspace](workspaces.md). Frontend project/auth integration is not implemented.

## Requests

- `POST /api/v1/workspaces/{workspace_id}/projects`: current owner, session cookie, exact Origin and `/me` CSRF token. Supply `name`, `goal`, nonempty `stack` and optional `architecture_notes`, `environment`, `constraints` strings.
- `GET /api/v1/workspaces/{workspace_id}/projects`: current members, ascending `(created_at,id)` cursor pagination; 25 default, 100 maximum. Cursors bind actor, workspace and list type.
- `GET /api/v1/projects/{project_id}`: current member of the project's workspace. Global project IDs are resolved using current membership, never request headers/query claims.
- `PATCH /api/v1/projects/{project_id}`: current owner, Origin/CSRF, positive integer `expected_revision` and at least one editable context field. An atomic revision check prevents lost edits and returns 409/`revision_conflict` when stale. Every accepted edit increments the revision; omitted fields stay unchanged, and empty optional strings clear fields.

Example create body:

```json
{
  "name": "Support assistant",
  "goal": "Build cited answers for our backend",
  "stack": [
    {"technology": "FastAPI", "docs_target": "0.115"},
    {"technology": "PostgreSQL"}
  ],
  "environment": "Local Docker"
}
```

Creation returns `{project, job_ids, pending_dependency_ids}` with HTTP 201. Dependency IDs are generated by the server; callers cannot provide IDs or declared/resolved versions. A docs target is an explicit requested version, not proof of package resolution or publisher/version approval. Omitted targets remain null and are never replaced with latest. Project text is trimmed; blank names/goals/technologies/targets, explicit null input, NUL characters, empty stacks and extra fields return safe 422. Optional context is represented as strings (empty when unset).

Exactly one manual stack or `stack_review_id` is required. Supplying both/neither is 422. GitHub scan/review storage does not exist yet, so reviewed-ID creation returns 501 without creating a project, collection, request or job. No repository binding can be submitted through manual context.

## Pending documentation and owner-only collections

One transaction creates project context, an owner-only `Default` collection and one private durable documentation request per dependency. Its ID matches the project dependency ID. Requests record requester, project/workspace, context revision, state and a safe reason: `version_unresolved` or `source_catalog_unavailable`. No raw goal/content or remote URL goes into these request records.

There are no approved source manifests/version selections, processing policies, budget admission or import workers yet. All manual dependencies therefore remain `pending_review`; `pending_dependency_ids` contains their IDs and `job_ids=[]`. These are persisted local requests, not dispatched/importing/ready jobs. No network, hosted processor or paid provider call is made. The future approval/import task must revalidate current authority, approved source scope and capacity before dispatch; this slice does not implement a queue consumer.

Editing other context updates the active requests' context revision. Replacing the stack supersedes old pending requests and assigns replacement dependency IDs with new pending requests, atomically with the revision. The default collection ID stays fixed. There is no existing imported knowledge to replace in this slice.

Current members can see project context and its default collection ID. Creation adds no read/write grants. The later [collection policy slice](collection-policy.md) implements owner-managed grants, grant-filtered collection metadata and separate project/collection processor consent; a default ID alone grants no content access. Project child stubs check current membership before returning 501; unknown, malformed and inaccessible project IDs share safe 404. Visible nonowners get 403/`forbidden` for project mutations. Removed members lose access on their next request.

## Storage, failure walkthrough and verification

Revision `0005_projects` first checks for nonempty legacy stacks. Earlier storage allowed arbitrary JSON arrays and had no runtime project writer, so such rows require operator review before migration: SQLSTATE `22023` stops the transaction without modifying context/schema. Do not clear real stack data to bypass this check; inventory it and prepare a reviewed conversion first. Existing empty-stack rows receive default collections without changing context. Composite project/workspace foreign keys and a unique default-collection index prevent invalid child associations. Narrow fixed-search-path functions are executable only by runtime; the documentation replacement helper and direct request table reads/writes remain private. General runtime project/collection writes remain denied. Creation and updates lock the workspace and recheck the current owner, sharing the membership mutation lock order.

Failure example: two owners edit revision 1 concurrently. One transaction commits revision 2; the other sees revision 2 after its lock wait and returns 409 without overwriting context or requests. A waiting actor who loses ownership receives 403. A failure inserting pending requests rolls back project/default collection insertion too.

Tests use only guarded disposable PostgreSQL:

```powershell
docker compose --profile test up -d --wait test-db
uv run --project backend --locked --cache-dir backend/.uv-cache pytest backend/tests -q -W error --tb=short
docker compose --profile test stop test-db
```

The original persistent development credentials remain unavailable after the prior reset. Development volumes were not reset or migrated; restore their original credentials before starting `db` or applying development migrations. Downgrading this revision drops collections and pending requests; it is not a production data-preserving rollback. Use a verified backup/recovery plan for persistent data.
