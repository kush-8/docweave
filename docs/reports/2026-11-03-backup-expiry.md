# Explicit recovery-backup expiry

Ordinary recovery backups can now be enrolled for seven-day expiry after actual restore/preservation verification. Enrollment binds the dump to its acceptance hash and seals every file. No archive is classified or enrolled automatically. The personal worker checks the repository backup root on startup and during its existing maintenance loop; hashing/deletion runs in a thread rather than blocking its event loop.

Five existing verified recovery sets are enrolled, with actual dump last-write timestamps cross-checked against their inventory. Expiry falls on November8–9UTC. No real deletion was due. The protected original accounting archive was fingerprinted before/after: all files match, and it has no expiry receipt. Unclassified directories and standalone reports remain outside expiry. Enrollment and live acceptance evidence is private in `backups/backup-expiry-enrollment-20261103.json` and `backups/backup-expiry-runtime-20261103.json`.

Before deleting, expiry validates the direct-child path, rejects links/junctions and requires all sealed file bytes to match. Added or removed evidence blocks a fresh deletion. A fsynced deletion marker precedes the first unlink. Locks and I/O failures report pending retry; remaining original bytes can be deleted on a later pass, while new or altered evidence blocks it. No recursive purge can swallow newly added files. Sealed backups require no concurrent writers; these checks do not defend against an adversarial local process swapping paths during unlink.

Review caught a partial-deletion retry failure and timestamp overflow. Both were reproduced with failing tests, corrected and independently re-reviewed. Fourteen focused tests pass, including the seven-day boundary, archive preservation, modified/added/missing evidence, path rejection, simulated junction detection, corrupt/extreme receipts and a locked-file retry. The actual worker-maintenance test deletes a disposable expired backup while preserving referenced/recent artifacts. Final complete verification passed727tests in218.34s with warnings as errors. Independently inspected `logs/backup-retention-final-20261103.xml`:727tests, zero failures/errors/skips.

The previous worker process was absent on a fresh OS inventory. With zero running queue jobs and zero enabled provider profiles, started the updated worker hidden (launcher53468). Read-only acceptance confirms a fresh queue heartbeat, development0041 and no due backups. No schema migration, private activation, extra paid call or commit occurred.

The operator must enroll each future verified ordinary backup, monitor blocked/pending statuses and maintain fresh recoverable backups separately. This does not yet establish deployed retention/backlog acceptance. Post-restore deletion replay is still missing: current HTTP deletion paths are chat deletion, document deletion and imported-source deletion. They use database transactions, but later tombstones are not durably retained outside old backups. A replay implementation must cover all three and preserve financial/replay IDs; restoring the old database alone cannot prove erasure.
