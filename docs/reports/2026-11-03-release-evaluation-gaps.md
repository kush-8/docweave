## Required result

Release acceptance requires 150 scenarios, split into 100 development and 50 held-out cases; separate 30-output development-calibration and release human reviews; Recall@10 >= 0.85; required-fact coverage >= 0.80; abstention recall >= 0.90; 100% structural citation validity; and no severe unsupported operational/security claims or unauthorized disclosures. Report denominators, false positives, latency and cost. Component tests cannot establish semantic quality. [PRD](../PRD.md#completion-criteria), [verification rules](../rules.md#verification). The separate review samples and actual-backend-turn requirement are recorded in [the confirmed evaluation protocol](../memory.md#backend-rag-planning-update--2026-10-30).

## Smallest complete evaluation work

1. **Add a release-specific dataset and validation path**, keeping the historical hash-pinned pilot unchanged. Reuse exact span/hash validation and atomic reports. Freeze 100 development and 50 held-out scenarios with globally unique IDs and family-disjoint splits, required facts/supports, expected answer/clarification/abstention or denial outcomes, version targets and multi-turn sequences. Include memory/context changes, policy/source/consent revocation, credential/injection cases and legitimate security examples for false-positive measurement. Record label review as pending until a person reviews it; a generated label is not a human review. The current schema alone is insufficient because it has no required-fact labels, expected answer outcome or conversation sequence.
2. **Extend evaluation around actual personal jobs**, reusing `AnswerEngine`, `run_personal_job`, ordinary provider admission and the integration fixture above. Capture immutable code/config/model/profile/generation/prompt/policy/dataset/corpus identities, per-turn context, eligible evidence, answers, exact citations, structured outcome, stage timings and actual/uncertain charges. Preserve access/consent/guardrails and idempotent operation identities. Private evaluation captures belong in ignored private operator storage. Do not feed expected answers/labels into provider prompts.
3. **Score the required outputs**, extending `evaluation/metrics.py` and writing through `evaluation/reports.py`. Keep ANN recall separate from supporting Recall@10. Capture the top ten retrieval/reranking candidates separately from the final evidence: current `ranked_evidence` intentionally caps final evidence at eight items ([reranking.py](../../backend/src/docweave/rag/reranking.py), lines 20-39). Measure required-fact coverage, abstention recall, structural citation validity, disclosure/severe-claim failures, guardrail detection and false positives, stage/end-to-end latency and cost with explicit matched/eligible denominators. `AnswerEngine.answer` renders and drops the structured `kind`; retain it in evaluation captures rather than inferring abstention solely from answer text ([answer_engine.py](../../backend/src/docweave/services/answer_engine.py), lines 182-204).
4. **Separate calibration from release.** Use development cases to select configuration and calibrate labels/review rubrics; freeze the chosen configuration before held-out execution. Export two distinct 30-output review packets with answer/evidence/reference identities and an empty rubric for correctness, relevance, faithfulness, citation support and severe errors. Collect actual human assessments; model judgments may supplement them, never impersonate them. If Groq judging is added, it needs an eligible role and ordinary verified admission; no evaluator bypass or new dependency is necessary merely to compute deterministic metrics.
5. **Verify focused behavior before any full run.** Add release-loader tests for split counts/family leakage/invalid spans/unreviewed labels; metric denominator and false-positive tests; one personal-job capture/reuse test with mocked HTTP; separate review-packet selection tests; and stale/missing evaluation-evidence rejection tests for readiness. Reuse `tests/evaluation/test_evaluation_protocol.py`, `tests/personal/test_personal_answer_pipeline.py`, `test_summary_persistence.py`, `test_personal_admission.py`, `tests/providers/test_answer_contract.py` and `tests/api/test_guardrail_http_release.py`. These checks prove the harness, not provider quality.

That is truthful while release gates remain open, but it is not an implemented readiness evaluator.

The smallest future readiness change is a service-owned, read-only check of existing operational state plus a verified release-acceptance artifact bound to the current configuration and implementation. Bind acceptance to dataset/splits, frozen source/config/policy/model identities, measured thresholds, completed distinct human-review packets, final billing disposition and cleanup/backup acceptance. Runtime checks additionally need available DB/schema, current guardrail policy, worker/recovery state and required eligible profiles/generation. Keep content and financial details out of anonymous health responses. Contract/test implications: `api/routes/health.py`, `schemas/health.py`, `api/errors.py`, `backend/openapi.yaml` and `tests/api/test_api.py`.

The draft and capture adapter are preparation, not full execution or release evidence.
